# Galio

Galio 是面向具身智能数据采集业务的运维平台，覆盖设备资产、监控告警、检测（体检/验收/发布核验/交接）、工单调度、发布管理、配置管理、采集业务等能力，目标是让上百个采集工位的可用性、故障处理与版本发布从"靠人盯人"变为系统化、可追溯、可统计。

> 当前仓库处于设计评审阶段，尚未包含代码实现。本 README 基于架构设计文档整理，作为项目总览与后续开发的参照。

## 背景与目标

具身智能数据采集业务依赖大量采集工位持续运转，每个工位由 **机械臂×N + 灵巧手 + 数据手套 + Quest 头显/手柄 + 摄像头×N + 采集主机** 组成。0828 复盘暴露的核心问题：

1. **状态黑盒**：所有节点和服务没有 checkpoint，设备能不能用、修没修好，只能上机试错；
2. **报修靠吼**：口头报修、多群通知，信息不到位，采集员甚至不愿上报；修好了没人知道，设备空等；
3. **发布不可信**：出现过"以为推了实际没推"（手部标定代码未推生产机），版本发布后无落地验证；
4. **人力断档**：早晚班运维能力不均、无交接机制，晚班调好的机器早班用不了；
5. **规模压力**：B 栋 100+ 台灵巧手即将部署，靠个别专家救火的模式无法扩展。

### 平台目标

| 目标 | 度量 |
|-|-|
| 任何一台设备上机前可判定是否可用 | 一键体检覆盖率 100%，上机前体检通过率可统计 |
| 故障全程可追溯、可统计 | 报修→派单→修复→验收 全链路系统化，响应/处理时长可导出 |
| 生产机版本可知、可控、可验证 | 每台机器版本清单实时准确，发布后自动核验 |
| 报修与修复从"靠自觉"到"可量化" | 故障时间自动剔除工时，考核数据自动产出 |
| 支撑 100+ 工位规模 | 单集群支撑 ≥200 工位，故障处理能力去中心化 |

### 非目标（本期不做）

- 不替代采集数据管道本身（数据上传、标注、质检属于数据平台）；
- 不做设备固件级 OTA（机械臂/灵巧手固件仍走厂商工具，平台只记录版本）；
- **不整合 Overwatch，但功能全覆盖并替代之**：不做系统对接、不桥接报障事件；Overwatch 的现有能力（手套报障、故障记录与导出、数据分析）全部由本平台原生实现（见[与 Overwatch 的关系](#与-overwatch-的关系)），上线并行验证后切流，Overwatch 下线；
- 不实现头显假死自动检测（复盘结论：走培训路线）、手套瞬断自动重连（推动供应商 wuji，平台只做检测计数）。

## 架构设计

Galio 服务端以无状态 api/worker 副本 + 单一 PostgreSQL 存储为核心：正确性（幂等、去重、互斥、任务领取）全部落在数据库，不引入 Redis/MinIO/消息中间件；工位端不部署常驻 Agent，服务端 Worker 通过 SSH/Ansible 主动连接工位执行探针脚本、下发检测与发布任务，主机基础指标复用各机已预装的 node_exporter；检测（体检/验收/发布核验/交接）与工单闭环状态机是平台的核心领域模型。

## 与 Overwatch 的关系

**决策：不做系统整合，由本平台功能全覆盖 Overwatch 并替代之**——不做对接桥接（避免维护两套系统间的接口），而是把 Overwatch 的能力作为本平台的原生功能实现，最终 Overwatch 下线。

### 功能对齐清单（替代的验收标准）

| Overwatch 现有能力 | 本平台承接位置 | 增强点 |
|-|-|-|
| 手套故障报修 | 统一报修入口（全设备类型） | 自动带工位/设备上下文，扩展到灵巧手等全部设备 |
| 故障记录 | 工单全生命周期记录 | 增加根因判定、验收关单 |
| 故障信息批量导出 | 工单导出 | 含处理人、响应时长、处理总时长 |
| 数据分析 | *本期不做*（原绩效统计/报表能力已从 v1 范围移除） | 需另行确认是否补齐，见 [R9](#风险与开放问题) |

### 替代切换计划

1. **并行验证期**（M1 试点，约 2 周）：新平台在 C 栋试点上线，手套报修双系统并行，每日核对两边数据完整性；
2. **切流**：功能对齐清单逐项验收通过后，运营侧发文统一报修入口到本平台，Overwatch 停止受理新报障；
3. **历史数据**：Overwatch 历史故障数据做一次性导出归档（CSV 入平台对象存储备查），**不做**实时数据迁移或双向同步；
4. **下线**：切流稳定运行 1 个月后 Overwatch 下线。

## 实施路线

| 阶段 | 范围 | 出口标准 |
|-|-|-|
| M1（P0，~6 周） | Worker 端 SSH/Ansible 巡检执行框架 + node_exporter 抓取 + quest/svc/link/env 探针脚本；状态大盘；系统报修 + 派单 + 时效记录 + 工单导出 + 超时提醒；飞书通知 | C 栋试点：口头报修清零，ADB/启动状态可区分；功能对齐 Overwatch，进入双系统并行验证 |
| M2（P1，~6 周） | 检测引擎四场景（体检/验收/发布核验/交接）；arm/hand/glove/camera 探针；发布流水线 + 版本对账 + 冻结；班次交接单 | 上机前体检强制化；发布逐机核验上线；报修切流至本平台，Overwatch 停止受理并进入下线观察期 |
| M3（P2，~8 周） | 区域责任与升级梯度 | B 栋 100+ 台规模化部署就绪 |

## 风险与开放问题

| # | 问题 | 建议/待定 |
|-|-|-|
| R1 | 替代 Overwatch 的切换风险：①功能对齐清单是否完整——需 Overwatch 实际使用者确认有无清单外的隐性能力；②并行期双入口数据分散；③历史数据归档格式与保留期限 | 切流前由手套运维用户走查对齐清单；并行期每日核对；历史数据一次性导出归档 |
| R2 | 各设备 SDK（机械臂/灵巧手/手套）能否在探针脚本临时执行时安全调用（依赖冲突、许可证、设备句柄是否被采集软件占用——探针不能与采集软件抢设备；每次 SSH 触发都是新进程，SDK 握手开销需评估是否影响巡检时效） | 需逐 SDK 做 PoC；原则：探针只读、可被采集软件抢占 |
| R3 | "启动慢 vs 坏"依赖被监控服务改造上报启动阶段，改造范围与排期 | 列出服务清单，优先改造高频误判的 2–3 个 |
| R4 | 摄像头画面检测（黑屏/花屏）的准确率标准 | M2 先规则启发式，误报率>10% 再评估模型方案 |
| R6 | 服务端部署位置：B/C 栋各一套 vs 一套覆盖两栋（跨栋网络质量） | 待网络勘测；架构上支持多站点 |
| R7 | 采集软件内嵌上报 SDK 需采集软件团队排期配合 | M1 可先用巡检探针脚本外部探测兜底 |
| R8 | 机械臂越线的根治（限位方案）超出平台范围 | 平台承接检测+告警；根治项单独立项跟踪 |
| R9 | 知识库（SOP）与绩效统计模块已从本版本范围移除，但 Overwatch 替代清单里的"数据分析"能力依赖绩效统计——功能对齐清单不再完整 | 需与 Overwatch 使用者确认"数据分析"能力是否必须在切流前补齐，或明确降级为不承接 |
| R10 | 不做常驻 Agent 后的能力降级：工位断网期间的指标数据无法本地缓存续传（真实空洞，补不回历史）；设备专属状态巡检降到分钟级（主机基础指标经 node_exporter 可达秒级） | 需确认该降级对"状态黑盒"目标是否可接受；如证明分钟级不够用，再评估对高价值场景（正在采集的工位）提高巡检频率 |
| R11 | 工位需对服务端网段开放 SSH 入站（原方案 Agent 纯出站，工位不开放任何入站端口）——网络策略变化需现场 IT/安全确认；SSH 私钥托管与轮换方案未定 | 上线前与现场网络负责人确认防火墙策略；M1 前定下密钥托管方案（Ansible Vault / 专用 secrets 存储） |
